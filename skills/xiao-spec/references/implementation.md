# 实现流程

仅在进入实现阶段时加载。每次只处理计划中第一个未完成且依赖已满足的任务。

## 单任务循环

1. 读取 `change.md` 中关联需求/场景和计划中当前任务，不重新解释未批准的范围。
2. 检查列出的源码、测试和依赖；若计划与实际代码冲突，先暂停并报告。
3. 写一个能证明目标行为的测试，或确认已有测试为何覆盖该行为。
4. 在可行时先运行测试观察失败或缺失证据；不要为了让测试通过而删除断言或降低范围。
5. 实施最小修改，避免顺手重构无关代码。
6. 运行任务要求的定向测试和必要的静态检查。
7. 做需求符合性审查，再做代码质量/回归审查。
8. 只有证据完整且没有未解决问题时，才勾选任务的 `- [ ] Task complete` 为 `- [x] Task complete`，再勾选已完成步骤。

## 完成记录

在任务下保留简短证据：运行的命令、结果摘要、验收场景覆盖情况、审查发现及处理方式。测试没有运行、输出属于更早代码、审查仍有问题或依赖任务未完成时，任务保持 `- [ ] Task complete`。证据中不得包含密码、Token、密钥、客户数据或完整日志。

## 子代理与串行回退

宿主提供子代理且任务相互独立时，可以委派单个任务；委派内容必须包含任务原文、相关需求、文件范围、验证命令和“不修改其他任务”的边界。子代理结果仍需主流程检查。

宿主不支持子代理时，当前会话串行执行。此时可以做两轮不同视角的审查，但必须说明它们不是独立代理审查，不得把工具缺失当成阻塞。

## 禁止事项

- 不修改已批准需求或任务来掩盖实现失败。
- 不用计划 checkbox 代替测试输出。
- 不自动 stash、reset、覆盖或清理启动前已有修改。
- 不把发现的新范围直接塞入当前任务；回到设计或计划审批。
