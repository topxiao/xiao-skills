# 调试与审查

实现遇到失败、异常行为或审查意见时加载。本文件把调试和审查变成可追溯的证据链。

## 系统化调试

按顺序执行：

1. **复现**：记录最小输入、实际结果、预期结果和失败命令。
2. **建立假设**：列出可能根因，优先检查最接近失败现象的路径。
3. **区分实验**：每次只改变一个变量，用结果淘汰假设，不反复盲目重试。
4. **定位根因**：说明失败为何发生以及为何不是相邻症状。
5. **修复**：先补能复现问题的回归测试，再做最小修复。
6. **回归**：重跑原失败测试、当前任务测试和受影响的相关测试。

测试失败、环境缺失或需求歧义必须如实报告；不得注释掉断言、跳过测试、添加绕过标记或把失败改写成成功。

## 两轮审查

### 需求符合性

- 每个关联需求和场景是否有实现与测试证据？
- 是否改变了批准的范围、接口、约束或非目标？
- 失败或未覆盖的验收项是否明确列出？

### 代码质量与回归

- 是否只修改了任务范围内的文件？
- 错误处理、边界条件、兼容性和安全约束是否合理？
- 是否引入重复逻辑、无关重构、脆弱测试或新的未验证依赖？

发现问题先修复并重新运行验证；无法安全修复时保持任务未完成并返回用户，不修改计划文本来消除问题。
