# 验证、恢复与归档

在阶段切换、恢复、最终验证和归档时加载。纯提示词版不提供 hash 快照、原子状态迁移或 CLI schema 校验；必须把证据和不确定性说清楚。不要把密码、Token、密钥、客户数据或完整日志写入 change、计划或验证记录。

## 阶段顺序与回退

阶段顺序见 SKILL.md 的「阶段与模式」。只有文件证据、测试结果或用户新指令支持回退时，才回到更早阶段。不得仅凭时间、目录排序或 checkbox 猜测恢复点。

## 阶段边界检查

- **设计 → 计划/实现**：`change.md` 存在且用户批准范围、非目标和验收场景。
- **计划 → 实现**：Standard/Fast 的计划已批准；任务有明确依赖、文件和验证方式。Mini 有且只有一个可验证任务。
- **实现 → 验证**：所有任务都有 `- [x] Task complete`，且满足测试和两轮审查证据；未完成项、失败项和未运行项都已处理。
- **验证 → 归档**：所有验收场景有本轮证据，相关测试/静态检查输出新鲜，变更范围已复核。
- **归档 → 完成**：长期规格（如有）已同步或明确不需要；归档位置已记录；用户要求的物理移动或 commit 已完成并核验。

## 新鲜验证

验证时重新运行计划中的命令，不使用旧日志、模型推断或“代码看起来正确”代替输出。最终报告按以下格式说明：

```text
已运行：<command> → <result>
未运行：<command> → <reason>
失败：<command> → <failure and current blocker>
验收覆盖：<scenario> → <evidence>
```

不得带未解决失败进入完成状态；终态按以下边界判定：

- 「未运行」指本轮无法执行且有明确理由的命令（需要人工操作、外部环境等）：记录理由后不阻塞完成。
- 「失败」指测试红、验收场景未覆盖、输出陈旧无法刷新或审查意见未解决：change 停在 `verification` 并标记 `blocked`，由用户决定修复、回设计/计划缩范围或取消，不得带失败进入归档完成。
- 没有测试可运行的 change，用计划中的检查方式和人工验证代替；这些检查必须有本轮证据，否则同样不得进入完成。

## 阶段字段与归档记录

阶段切换时按下表更新 `change.md` frontmatter；不要另建状态 JSON。

| 事件 | `phase` | `status` |
|---|---|---|
| 设计获批，Standard/Fast 进入计划 | `plan` | `active` |
| 设计获批，Mini 进入实现 | `implementation` | `active` |
| 计划获批并开始实现 | `implementation` | `active` |
| 所有任务完成并开始验证 | `verification` | `active` |
| 验证证据完整并开始归档 | `archive` | `active` |
| 归档完成 | `completed` | `completed` |
| 当前阶段无法继续 | 保留当前阶段 | `blocked` |
| 用户明确放弃该 change | 保留当前阶段 | `cancelled` |

每次用户批准设计或计划时更新 `approved_at`；模式升级时同步更新 `mode`。阶段字段只反映证据已经达到的阶段，不得提前填写。

取消时在 Decisions and Open Questions 记录原因和遗留状态；change 目录保留，除非用户明确要求删除；已产生的代码修改由用户决定去留，不自动回滚。恢复已取消的 change 需用户明确要求：把 `status` 改回 `active`，并重新确认当前阶段所需的批准。归档完成时将 `phase` 和 `status` 更新为 `completed`，并把日期和位置写入已有 `archive_path` 字段。除非项目已有明确约定，不新增第三份归档文档。

## 漂移与恢复

1. 先读取 `change.md` frontmatter 和正文，再读取 `implementation-plan.md` 当前任务。
2. `change.md` 的 `xiao_spec_version` 与当前 skill 版本不一致时，先说明差异并取得用户确认再继续。
3. Git 可用时检查 `git status --short`、相关 `git diff` 和启动前脏文件；Git 不可用时使用批准的文件清单，并将范围结论标为低可信度。
4. `change.md` 的目标/范围/约束/设计/验收改变 → 回设计，重新取得批准。
5. 计划任务、依赖、文件路径或验收映射改变 → 回计划，重新取得批准。
6. 仅 checkbox 或任务证据改变 → 属于进度变化，不要误判为计划内容漂移。
7. 找不到文档、状态冲突、无法区分用户既有修改或无法确认完成证据 → 暂停，报告冲突，不猜测、不覆盖。

## 启动前已有修改

启动时记录的 `initial_dirty_paths` 只用于识别边界，不得自动纳入当前 change 的提交或归档范围。不能安全区分时，停止并让用户决定；不得 stash、reset、删除或清理。

## 归档

默认在 change 目录写入归档日期、最终状态和归档位置。只有用户明确要求时才物理移动、重命名或 commit；移动后检查源路径和目标路径，commit 后记录真实 hash。不要要求整个工作树干净，也不要把无关修改混进范围。

若仓库已有 `docs/specs/` 或其他长期规格，仅在该变更确实更新稳定契约时同步；没有长期规格就不要为了归档复制一套新 spec。
